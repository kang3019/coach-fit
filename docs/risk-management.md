## ⚠️ 1. 카테고리별 위험 식별 및 대응 방안

---

### 위험 1: Android 실기기 / 에뮬레이터 HTTP 통신 보안 차단 (Cleartext Traffic)
- **카테고리**: 기술 위험
- **발생 가능성**: 상 (Android 9.0 이상 기본 차단)
- **영향도**: 상 (앱에서 서버 데이터를 전혀 불러오지 못함)
- **대응 방안**:
  - **예방**: `AndroidManifest.xml`에 `android:usesCleartextTraffic="true"` 명시 및 로컬 IP 자동 분기(`ApiConstants`) 설정 완료.
  - **발생 시**: Windows 데스크톱 모드(`flutter run -d windows`), Chrome 웹 모드(`flutter run -d chrome`) 또는 Android 에뮬레이터 루프백(`10.0.2.2:8000`)으로 신속 전환.
- **모니터링 지표**: 모바일 앱 구동 즉시 초기 5건의 운동 기록이 정상 로딩되는지 확인.

---

### 위험 2: 외부 LLM API 호출 지연, 할당량 초과(Quota Exceeded) 또는 네트워크 단절
- **카테고리**: AI 의존 위험
- **발생 가능성**: 중
- **영향도**: 상 (AI 추천 화면에서 10초 이상 무한 로딩 또는 500 에러 발생)
- **대응 방안**:
  - **예방**: Python FastAPI 서버에 **'하이브리드 스마트 룰베이스 폴백 엔진'** 상시 내장. OpenAI/Claude 호출 실패 시 0.1초 만에 최적의 룰베이스 루틴 자동 생성.
  - **발생 시**: 앱 사용자에게는 끊김 없이 분석 결과 카드가 즉시 렌더링되며, 백엔드 콘솔에만 폴백 로그 기록.
- **모니터링 지표**: AI 코칭 요청 응답 시간이 2초 이내로 유지되는지 여부.

---

### 위험 3: 학업/개인 일정 및 본업 일정으로 인한 개발 지연
- **카테고리**: 일정 위험
- **발생 가능성**: 상
- **영향도**: 중
- **대응 방안**:
  - **예방**: WBS에 **20% 버퍼(약 11 Man-Day)**를 사전 배정. 10월 중순(11주차)까지 핵심 Must 기능의 50% 이상을 선제 개발.
  - **발생 시**: Should/Could 기능(다크 모드, 소셜 목표 등)을 과감히 동결하고, '운동 기록 CRUD + AI 루틴 추천' 핵심 2개 플로우에만 인력 집중.
- **모니터링 지표**: WBS 주차별 계획 대비 실제 구현 진척률 (주 1회 점검).

---

### 위험 4: 2인 협업 시 모바일 ↔ 백엔드 간 REST API 스펙 불일치 및 통신 충돌
- **카테고리**: 협업 위험
- **발생 가능성**: 중
- **영향도**: 중 (파싱 에러로 인해 화면 깨짐)
- **대응 방안**:
  - **예방**: FastAPI Pydantic v2 스키마(`schemas.py`) 및 Flutter 데이터 모델(`models/`)을 상호 일치시키고, Swagger 문서(`http://localhost:8000/docs`)를 기준으로 소통.
  - **발생 시**: Git PR 리뷰 단계에서 API 변경 시 DTO 필드 호환성 상호 확인 후 머지.
- **모니터링 지표**: Flutter 앱 내 JSON 직렬화/역직렬화 오류 발생 건수 0건 유지.

---

### 위험 5: 11/20 최종 데모 현장 Wi-Fi 단절 및 발표 환경 장애
- **카테고리**: 결과물 / 데모 위험
- **발생 가능성**: 중
- **영향도**: 최상 (데모 발표 성공 여부에 직접적인 타격)
- **대응 방안**:
  - **예방**:
    1. 외부 인터넷 없이 노트북 로컬(`localhost` + SQLite DB `coachfit.db`)에서 완벽히 독립 구동되도록 설계.
    2. 발표 3일 전, 실제 스마트폰 화면 녹화 데모 영상(Backup Video)을 1080p 고화질로 사전 촬영하여 PPT 슬라이드에 임베딩.
  - **발생 시**: Wi-Fi 접속이 불가하거나 서버 오류 시 즉시 백업 데모 영상으로 전환하여 발표 진행.
- **모니터링 지표**: 오프라인(비행기 탑승 모드) 환경에서의 앱 정상 시연 테스트 통과 여부.

## 🎤 2. 최종 데모 Q&A 단골 질문 대비 모범 답변

### Q1. "프로젝트 진행 중 겪은 가장 큰 기술적 위험은 무엇이었고, 어떻게 해결했나요?"
> **모범 답변**:  
> "가장 큰 위험은 **'외부 AI LLM의 불확실성(네트워크 지연 및 API 할당량 장애)'**이었습니다. 실시간 운동 중인 사용자가 AI 추천 버튼을 눌렀을 때 5~10초간 대기하거나 오류가 나면 서비스 신뢰도가 급격히 하락합니다.  
> 이를 해결하기 위해 저희 팀은 **'하이브리드 AI 폴백 아키텍처(ADR-0003)'**를 구축했습니다. 외부 LLM 호출이 지연되거나 실패할 경우, 직전 운동 부위의 피로도를 알고리즘으로 즉시 계산하는 스마트 룰 엔진이 0.1초 만에 최적의 루틴을 안전하게 대체 생성하도록 구현하여 100% 서비스 연속성을 보장했습니다."

### Q2. "2인 팀으로 진행하면서 일정 지연이나 역할 분담 갈등은 없었나요?"
> **모범 답변**:  
> "저희 팀은 초기 WBS 단계에서 **20%의 일정 버퍼**를 확보하고, 지도 교수님의 피드백을 수용하여 백엔드를 **FastAPI 단일 백엔드로 통합(ADR-0004)**한 뒤 클라이언트(Flutter)와 서버/AI(FastAPI)를 분리하는 **계층형 분업 모델(03-team-and-git-convention)**을 채택했습니다.  
> 각자의 코드 영역이 명확히 분리되어 Git 머지 충돌을 사전에 차단할 수 있었고, 주기적인 스프린트 리뷰 24시간 전에 항상 사전 통합 시연(Dry Run)을 진행하여 일정을 안정적으로 통제했습니다."
