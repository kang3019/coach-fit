[ Slide 1 — 인트로 / 약 10초 ]

AI(에이아이) 맞춤형 피트니스 코칭 및 3D(쓰리디) 근육 해부도 플랫폼,
CoachFit(코치핏) 프로젝트 발표를 맡은 강민권입니다.

[ Slide 2 — 문제 정의 (Why CoachFit?) / 약 25초 ]

먼저 저희가 왜 이 앱을 만들었는지 말씀드리겠습니다.
혼자 헬스장에 간 초보자가 가장 많이 겪는 장벽은
"어제 가슴 운동을 했는데, 오늘은 무슨 운동을 몇 킬로그램으로 몇 세트 해야 하지?"라는 막막함입니다.

회당 5~8만 원에 달하는 PT(피티) 비용은 부담스럽고,
기존 인기 운동 기록 앱인 Fleek(플릭) 등은 세트 기록 UX(유엑스)는 훌륭하지만
누적된 데이터를 바탕으로 "오늘 할 루틴"을 역제안해주지는 못합니다.
또 생소한 운동 이름만 나열되어 어느 근육에 자극이 가는지 직관적으로 알기 어렵습니다.

그래서 저희는 3초 다중 세트 기록 UX(유엑스)에,
실제 3D(쓰리디) 인체 해부도 동적 점등과
DB(디비) 직결 AI(에이아이) 맞춤형 당일 루틴 추천을 결합하여 이 세 가지 문제를 해결했습니다.

                                       → 슬라이드 전환 키워드: "해결했습니다"

[ Slide 3 — 우리의 비전 (Our Vision) / 약 15초 ]

따라서 CoachFit(코치핏)의 핵심 비전은
단순한 운동 수첩을 넘어, "기록할수록 똑똑해지는 주머니 속 AI(에이아이) 전담 트레이너"입니다.
오늘 헬스장에서 뭘 할지 고민하는 시간을 0초로 줄이고,
추천받은 루틴을 원터치로 오늘 기록에 담아 즉시 운동을 시작하게 만듭니다.

                                       → 슬라이드 전환 키워드: "바로 시작하게 만듭니다"

[ Slide 4 — 프로젝트 계획 & WBS 진행 현황 / 약 20초 ]

프로젝트 계획은 MoSCoW(모스코우) 기법으로 범위를 명확히 통제했습니다.
운동 CRUD(씨알유디), 볼륨 통계, AI(에이아이) 루틴 추천, 스마트 폴백을 Must(머스트)로 두고,
일정 지연 위험이 큰 카메라 비전 자세 교정과 웨어러블 연동은 Won't(원트)로 과감히 배제했습니다.

전체 일정에 20%의 버퍼를 두고 10주차부터 16주차까지 총 7개 마일스톤,
90여 개의 PR(피알)을 통해 현재 WBS(더블유비에스) 100%를 달성했습니다.

                                       → 슬라이드 전환 키워드: "100% 달성했습니다"

[ Slide 5 — 사용자 시나리오 / 약 25초 ]

실제 사용자의 하루 운동 흐름을 보겠습니다.
헬스 2주 차 민수 씨가 퇴근 후 앱을 켜서 컨디션을 체크하면,
AI(에이아이)가 어제 가슴 운동 기록을 확인하고 오늘은 등·후면 사슬 루틴을 추천하며
3D(쓰리디) 해부도에 타겟 근육을 실시간으로 점등해 줍니다.

'추천 루틴 시작하기'를 누르면 오늘 기록에 종목이 일괄 추가되고,
세트를 체크할 때마다 휴식 타이머가 자동으로 돌아갑니다.
주말에는 통계 탭에서 주간·월간·3개월 볼륨 추이와 인바디 변화를 점검하고
AI(에이아이) 1:1 코치와 부족한 부위를 상담합니다.

                                       → 슬라이드 전환 키워드: "상담합니다"

[ Slide 6 — 구현 방법 설명 / 약 25초 ]

핵심 기능인 AI(에이아이) 루틴 생성과 3D(쓰리디) 해부도 점등의 코드 흐름입니다.

홈 탭에서 코칭을 요청하면 FastAPI(패스트에이피아이) 백엔드가
DB(디비)에서 최근 10개 운동 세션과 최신 인바디, 목표를 직접 조회합니다.
이때 날짜와 프로필, 운동 기록을 SHA-256(샤 이오육)으로 해싱한 지문 캐시(CoachingCache)를 먼저 대조해,
같은 날 기록 변경이 없다면 LLM(엘엘엠) 재호출 없이 0.01초 만에 결과를 반환합니다.

반환된 루틴의 운동명과 타겟 텍스트를 Flutter(플러터)의 MuscleMapWidget(머슬맵 위젯)이 파싱하여,
인위적인 원형 번짐 대신 베이스 인체 해부도 위에 10종의 부위별 정밀 투명 PNG(피엔지) 레이어를
Stack(스택)으로 동적 적층해 타겟 근육을 정확히 점등합니다.

                                       → 슬라이드 전환 키워드: "정확히 점등합니다"

[ Slide 7 — 아키텍처 의사결정 (ADR) / 약 20초 ]

주요 기술적 의사결정은 4가지 ADR(에이디알)로 기록했습니다.
첫째, 모바일과 웹 데모를 단일 코드로 배포하기 위해 Flutter(플러터)를 선택했고,
둘째, 초기 Java(자바)와 Python(파이썬) 이중 서버 구조의 오버엔지니어링을 탈피해
교수님 피드백을 반영한 FastAPI(패스트에이피아이) + PostgreSQL(포스트그레스큐엘) 단일 백엔드로 통합했습니다.
셋째, 외부 AI(에이아이) 장애에도 100% 동작하는 5단 멀티 LLM(엘엘엠) 및 하이브리드 폴백을 구축했고,
넷째, 다중 레이어 3D(쓰리디) 해부도로 시각적 정밀도를 확보했습니다.

                                       → 슬라이드 전환 키워드: "확보했습니다"

[ Slide 8 — 앱 구조 & 아키텍처 다이어그램 / 약 20초 ]

전체 아키텍처와 디렉터리 구조입니다.
모바일 앱이 직접 외부 AI(에이아이)나 DB(디비)를 호출하지 않고,
반드시 포트 8000번 FastAPI(패스트에이피아이) 단일 백엔드를 경유하는 BFF(비에프에프) 패턴을 준수합니다.
백엔드는 SQLAlchemy(에스큐엘알케미) ORM(오알엠)으로 AWS RDS(알디에스) 및 로컬 SQLite(에스큐라이트)와 통신하며,
AWS Bedrock(베드락)과는 API(에이피아이) 키가 코드에 전혀 없는 IAM(아이엠) 역할 기반으로 안전하게 통신합니다.

                                       → 슬라이드 전환 키워드: "안전하게 통신합니다"

빌드와 배포 파이프라인입니다.

AWS 서울 리전 EC2(이씨투) 서버가 최신 코드를 pull(풀) 받고 systemd(시스템디) 서비스를 재시작한 뒤,
헬스체크까지 자동으로 완료합니다.

[ Slide 11 — 구현 시행착오 사례 / 약 30초 ]

개발 과정에서 겪은 네 가지 핵심 시행착오와 해결 과정입니다.

첫째, 초기 Java(자바)와 Python(파이썬) 두 개의 서버를 운영하다 DTO(디티오) 중복과 메모리 부담을 겪었고,
FastAPI(패스트에이피아이) 단일 백엔드로 통합해 개발 속도를 3배 높였습니다.

둘째, 해부도 초기 버전에서 drawOval(드로우오벌) 원형 블러를 썼더니 실제 근육 모양과 괴리가 커서,
이를 전면 폐기하고 10개 부위별 정밀 PNG(피엔지) 다중 레이어 구조로 재설계했습니다.

셋째, LLM(엘엘엠)이 가끔 세트 수를 null(널)로 반환하거나 재배포 후 토큰이 만료되면 루틴 카드가 깨지는 문제가 있었는데,
백엔드 안전 파서와 데모 세션 자동 복구, 클라이언트 스마트 폴백을 구축해 완벽히 해결했습니다.

넷째, CI/CD(씨아이씨디) 중 서드파티 SSH(에스에스에이치) 액션 504 장애와 Flutter(플러터) 버전 차이를 겪어,
네이티브 OpenSSH(오픈에스에스에이치) 배포와 SDK(에스디케이) 버전 고정으로 파이프라인을 안정화했습니다.

                                       → 슬라이드 전환 키워드: "안정화했습니다"

[ Q1 ] "왜 초기 Java + Python 2개 서버에서 FastAPI 단일 백엔드로 바꿨나요?" (ADR-0004)

가장 큰 이유는 '2인 팀 규모에 맞는 아키텍처 최적화'입니다.
초기에는 Spring Boot(스프링 부트, 8080 포트)와 FastAPI(패스트에이피아이, 8000 포트)를 분리했으나,
동일한 운동 데이터 DTO(디티오)를 양쪽 언어로 중복 정의해야 했고,
서버 간 내부 HTTP(에이치티티피) 통신 비용과 JVM(제이브이엠) 메모리 점유율 문제가 발생했습니다.
지도 교수님의 피드백을 적극 수용하여 포트 8000번 FastAPI(패스트에이피아이) + PostgreSQL(포스트그레스큐엘)
단일 백엔드로 통합한 결과, 보일러플레이트가 사라져 개발 속도가 3배 빨라졌고
AWS 프리티어 EC2(이씨투, RAM 1GB)에서도 메모리 부족 없이 24시간 안정적으로 구동되고 있습니다.

----------------------------------------------------------------


[ Q2 ] "OpenAI나 Gemini 대신 왜 AWS Bedrock(베드락)을 도입했나요? 과금 폭탄 위험은 없나요?"

두 가지 공학적 이유입니다.
첫째, '무키(Zero-Key) 보안'입니다. 외부 API(에이피아이)는 서버에 비밀키(sk-...)를 저장해야 해서 유출 위험이 크지만,
AWS Bedrock(베드락)은 EC2(이씨투)에 부여된 IAM Role(아이엠 롤)을 통해 코드에 단 한 글자의 비밀키도 없이 안전하게 인증됩니다.
둘째, '과금 방어 3중 안전망'을 구축했습니다.
백엔드 메모리에 SHA-256(샤 이오육) 지문 캐시(CoachingCache)를 두어 같은 날 운동 기록이 바뀌지 않으면 LLM(엘엘엠)을 다시 호출하지 않고,
AiRateLimiter(에이아이 레이트 리미터)로 분당 10회, 일일 100회 상한을 걸었으며,
평소 테스트 시에는 무료 Groq(그록)이나 스마트 룰 엔진으로 동작하도록 설계했습니다.

[ Q3 ] "코드 흐름 설명해 보세요 — AI 추천 루틴과 3D 근육 해부도는 어떻게 연결되나요?"

크게 4단계로 흐릅니다.

  1단계 — 클라이언트 요청 (CoachingService.requestCoaching)
  사용자가 홈 탭에 진입하거나 목표를 바꾸면 `POST /api/coaching/generate`를 호출합니다.
  만약 로컬 토큰이 만료되어 401이 뜨면 데모 세션을 자동 재발급해 재시도합니다.

  2단계 — 백엔드 DB 직결 조회 및 캐시 대조 (app/main.py)
  서버는 클라이언트 입력만 믿지 않고, DB(디비)에서 해당 유저의 최근 10개 운동 기록(`get_recent_workouts`),
  최신 인바디(`get_latest_body_metric`), 프로필 목표를 직접 조회해 `CoachingRequest`를 조립합니다.
  이후 `coaching_cache.fingerprint()`로 해시를 떠서 캐시 히트 시 즉시 반환합니다.

  3단계 — 멀티 LLM 추론 및 안전 파싱 (app/services/ai_coach.py)
  캐시가 없으면 설정된 `AI_PROVIDER`에 따라 Bedrock(베드락) 등을 호출하고,
  `_safe_routine_list()` 함수가 LLM(엘엘엠)의 비정형 JSON(제이슨)이나 null(널) 값을 안전하게 정제합니다.
  만약 LLM(엘엘엠) 호출 자체가 실패하면 0.1초 만에 `_generate_smart_dummy_coaching()` 규칙 엔진이 대체 루틴을 생성합니다.

  4단계 — 3D 해부도 다중 레이어 렌더링 (RecommendedRoutineCard -> MuscleMapWidget)
  프론트엔드는 반환된 루틴 종목들의 이름과 `focus` 문자열에서 `MuscleGroupExtension.parseFromText()`로
  활성 근육 Set(셋)을 추출하고, `body_base_neutral.png` 위에 해당 근육의 투명 `overlay_*.png` 이미지들을
  Stack(스택)으로 겹쳐 실시간 점등합니다.

[ Q4 ] "발표장 와이파이가 끊기거나 외부 LLM 서버가 죽으면 앱이 멈추지 않나요?"

절대 멈추지 않도록 '이중 하이브리드 폴백(Dual Fallback)'을 구현했습니다.
첫째, 백엔드 단에서 외부 LLM(엘엘엠)이 타임아웃되거나 에러를 내면 즉시 내장된 스마트 규칙 엔진이
사용자의 최근 운동 볼륨과 체중 대비 강도를 계산해 0.1초 만에 루틴을 내려줍니다.
둘째, 아예 모바일 기기와 서버 간 네트워크가 끊기거나 호출 한도(429)에 걸리더라도,
프론트엔드 `CoachingService`가 예외를 포착해 `CoachingResult.fallback(goal)`을 반환하므로
홈 화면의 3D(쓰리디) 해부도와 루틴 시작 기능은 어떤 상황에서도 100% 정상 동작합니다.

[ Q5 ] "어디서부터 어디까지 AI 코딩 도구를 활용했고, 본인이 직접 설계·검증한 부분은 무엇인가요?"

AI(에이아이) 에이전트를 코드 초안 작성, 리팩토링, 문서 구조화에 적극 활용했습니다.
하지만 아키텍처 전환 결정(폴리글랏에서 FastAPI 단일 백엔드로 통합),
3D(쓰리디) 해부도의 원형 블러를 폐기하고 다중 레이어 에셋 구조로 바꾼 UX(유엑스) 의사결정,
그리고 기간별(주간·월간·3개월) 볼륨 집계 로직과 2중 폴백 안전장치 설계는 저희가 직접 주도했습니다.
특히 모든 코드는 `pytest` 39개 테스트와 `flutter analyze` 무결성 검증을 통과할 때만 PR(피알)로 병합했습니다.

[ Q6 ] "2인 팀에서 Git 충돌 없이 어떻게 협업했나요?"

모노레포 내에서 프론트엔드(`mobile-app/`)와 백엔드(`python-ai-backend/`) 폴더를 계층형으로 분담하고,
FastAPI(패스트에이피아이)가 자동 생성하는 Swagger(`/docs`) 명세를 단일 계약(Single Source of Truth)으로 삼았습니다.
또한 `AGENTS.md` 규칙에 따라 `main` 브랜치 직접 커밋을 엄격히 금지하고,
모든 작업을 `feature/` 및 `fix/` 브랜치에서 수행한 뒤 GitHub PR(피알)과 CI(씨아이) 자동 검증을 거쳐 병합했습니다.
