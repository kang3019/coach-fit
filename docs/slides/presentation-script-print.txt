[ Slide 2 — 문제 정의 (Why CoachFit?) / 35초 (누적 0:50) ]

혼자 헬스장에 간 초보자가 매일 겪는 장벽은
"어제 가슴 했는데, 오늘 뭘 몇 kg으로 몇 세트 하지?"라는 막막함입니다.

회당 5~8만 원 PT는 부담스럽고, 기존 기록 앱은 수첩 기능은 좋지만
누적 데이터를 분석해 오늘 할 루틴을 역제안해주지 못합니다.
또 생소한 종목명만 나열돼 어느 근육에 자극이 가는지 알기 어렵습니다.

저희는 3초 세트 기록, 정밀 근육 해부도, DB 직결 AI 맞춤 루틴을 결합해
이 세 가지 문제를 해결했습니다.

[ Q1 ] "왜 초기 Java + Python 이중 서버에서 FastAPI 단일 백엔드로 바꿨나요?" (Slide 8, 11)

가장 큰 이유는 '2인 팀 규모와 프리티어 인프라에 맞는 아키텍처 최적화'입니다.
초기에는 Spring Boot(8080)와 FastAPI(8000)를 분리했으나,
동일한 운동 데이터 DTO를 양쪽 언어로 중복 정의해야 했고,
서버 간 내부 HTTP 통신 지연과 JVM 메모리 점유율 문제가 발생했습니다.
지도 교수님의 피드백을 수용해 포트 8000번 FastAPI + PostgreSQL 단일 백엔드로 통합한 결과,
보일러플레이트가 사라져 개발 속도가 3배 빨라졌고
AWS 프리티어 EC2(RAM 1GB)에서도 OOM 없이 24시간 안정적으로 운영되고 있습니다.

----------------------------------------------------------------


[ Q2 ] "OpenAI나 Gemini 대신 왜 AWS Bedrock을 도입했나요? 과금 폭탄 위험은 없나요?" (Slide 7, 9)

두 가지 공학적 이유입니다.
첫째, '무키(Zero-Key) 보안'입니다. 외부 API는 서버에 비밀키(sk-...)를 저장해야 해 유출 리스크가 크지만,
AWS Bedrock은 EC2에 부여된 IAM Role을 통해 코드에 단 한 글자의 비밀키도 없이 인증됩니다.
둘째, '과금 방어 3중 가드'를 구축했습니다.
SHA-256 지문 캐시(CoachingCache)로 같은 날 운동 기록 변화가 없으면 LLM을 재호출하지 않고,
AiRateLimiter로 사용자당 분당 10회·일 100회·전역 300회 상한을 걸었으며,
평소 테스트 시에는 무료 Groq이나 내장 스마트 룰 엔진으로 동작하도록 설계했습니다.

----------------------------------------------------------------


[ Q3 ] "코드 흐름을 설명해 보세요 — AI 추천 루틴과 근육 해부도는 어떻게 연결되나요?" (Slide 6)

크게 4단계로 흐릅니다.
1) 클라이언트 요청(CoachingService.requestCoaching): 홈 진입·목표 변경 시 `POST /api/coaching/generate` 호출.
   만료 토큰으로 401이 뜨면 데모 세션을 자동 재발급해 재시도합니다.
2) 백엔드 DB 직결 조회 & 캐시 대조(app/main.py): DB에서 최근 10세션, 최신 인바디, 목표를 조회해
   `coaching_cache.fingerprint()` 해시를 대조하고 히트 시 0.01초 만에 반환합니다.
3) 멀티 LLM 추론 & 안전 파싱(app/services/ai_coach.py): Bedrock 등을 호출한 뒤
   `_safe_routine_list()`가 null/문자열 같은 비정형 응답을 정제하며, 실패 시 0.1초 룰 엔진이 대체합니다.
4) 89-Path SVG 근육 점등(RecommendedRoutineCard -> MuscleMapWidget):
   종목명과 focus 문자열을 `MuscleGroupExtension.parseFromText()`로 10대 근육 그룹으로 파싱하고,
   `svg_body_data.dart`의 89개 해부학 SVG 패스(전면 40 + 후면 49)에 `#FF4820` 네온 글로우를 실시간 점등합니다.

[ Q4 ] "근육 해부도가 3D PNG에서 SVG로 바뀐 이유가 뭔가요?" (Slide 6, 11)

시각적 정밀도와 사용자 인터랙션 확장 때문입니다.
1단계 `drawOval` 원형 블러는 실제 근육 모양과 괴리가 커 폐기했고,
2단계 `anatomy_3d_display.dart`의 3D PNG 다중 레이어(베이스 + 10종 투명 PNG)로 개선했으나,
다양한 해상도 대응과 개별 근육 터치 필터링에 한계가 있었습니다.
최종 3단계로 89개 정밀 해부학 SVG 벡터 패스(`svg_body_data.dart`)를 적용해
Front/Back 듀얼 뷰에서 어떤 화면 크기에서도 깨지지 않고, 부위 뱃지 탭 시 즉시 강조·필터링되도록 완성했습니다.

[ Q5 ] "발표장 와이파이가 끊기거나 외부 LLM 서버가 죽으면 앱이 멈추지 않나요?" (Slide 7, 10)

절대 멈추지 않도록 '이중 하이브리드 폴백(Dual Fallback)'을 구현했습니다.
백엔드 단에서 외부 LLM이 타임아웃되거나 에러를 내면 0.1초 만에 스마트 룰 엔진이
사용자의 최근 볼륨과 체중 대비 강도를 계산해 루틴을 내려주고,
모바일과 서버 간 네트워크 자체가 끊기거나 레이트 리밋(429)에 걸려도
프론트엔드 `CoachingService`가 `CoachingResult.fallback(goal)`을 반환해 홈 화면과 루틴 시작이 100% 동작합니다.
또한 로컬 FastAPI + SQLite 시드 데이터로 완전 오프라인 시연도 가능합니다.

[ Q6 ] "어디서부터 어디까지 AI 코딩 도구를 썼고, 직접 설계·검증한 부분은 무엇인가요?" (Slide 8, 12)

AI 에이전트는 보일러플레이트 초안 작성, 리팩토링, 문서 구조화에 적극 활용했습니다.
하지만 이중 서버에서 FastAPI 단일 통합을 결정한 ADR-0004,
근육 해부도를 원형 블러→3D PNG→89-Path SVG로 진화시킨 UX 설계,
주간·월간·3개월 기간별 볼륨 집계와 이중 폴백 안전망 설계는 저희가 직접 주도했습니다.
특히 모든 코드는 `pytest` 39건과 `flutter analyze` 경고 0건을 통과할 때만 PR 병합했습니다.

[ Q7 ] "2인 팀에서 Git 충돌 없이 어떻게 협업했나요?" (Slide 9, 12)

모노레포 내에서 프론트엔드(`mobile-app/`)와 백엔드(`python-ai-backend/`)를 계층형으로 분담하고,
